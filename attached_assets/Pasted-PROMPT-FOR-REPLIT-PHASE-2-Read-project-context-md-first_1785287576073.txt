PROMPT FOR REPLIT — PHASE 2

Read project_context.md first for full context before starting.

This phase builds the core audit engine. Read this carefully — the
async pattern matters for our hosting constraint (single process, no
Redis/queue service).

1. Add an Audit model:
   - siteId (ref Site)
   - status: enum ['queued','running','done','failed'], default 'queued'
   - startedAt, completedAt
   - error (string, nullable — populate if status is 'failed')
   - results: {
       pagesCrawled: [string] (URLs actually fetched),
       technical: {
         missingMetaDescriptions: [url],
         missingTitleTags: [url],
         duplicateTitles: [{ title, urls: [url] }],
         headingIssues: [{ url, issue }],   // e.g. no H1, multiple H1s
         missingAltText: [{ url, imageCount }],
         robotsTxt: { found: bool, disallowsEverything: bool },
         sitemapXml: { found: bool, urlCount: number },
         brokenInternalLinks: [{ fromUrl, brokenUrl, status }]
       }
     }

2. Build backend/services/agents/technicalSeoAgent.js:
   - Takes a domain, fetches the homepage with axios, parses with
     cheerio, extracts all internal links (same domain only)
   - Crawls up to 20 pages total (hard cap — do not exceed this,
     it's a resource limit for our hosting)
   - Respect robots.txt: fetch /robots.txt first, skip any disallowed
     paths
   - For each page fetched, extract: title tag, meta description,
     H1/H2 structure, image alt text presence, internal links (to
     check for broken links — a HEAD request with a short timeout,
     e.g. 5s, treat failures/4xx/5xx as broken)
   - Add a small delay between requests (e.g. 300-500ms) to be a
     polite, non-aggressive crawler — this is someone's own site or a
     site they're auditing for legitimate SEO purposes, but we still
     don't want to hammer any server
   - Set a realistic User-Agent header identifying this as an SEO
     audit tool (not a fake browser UA) — be transparent about what
     this bot is
   - Return the structured results object matching the Audit model's
     "technical" shape above

3. Async job pattern (no Redis, no BullMQ):
   - POST /api/sites/:id/audit — creates an Audit doc with status
     'queued', immediately responds with { success: true, data: {
     auditId } }, then asynchronously (don't await in the request
     handler — fire and forget, same pattern as background scrape
     triggers) sets status to 'running', runs
     technicalSeoAgent.run(site.domain), writes the result and sets
     status 'done' (or 'failed' with the error message if it throws)
   - GET /api/sites/:id/audit/latest — returns the most recent Audit
     doc for that site, so the frontend can poll it
   - Add a safety timeout: if an audit has been 'running' for more
     than 5 minutes, a cron job (node-cron, every 1 minute) should
     mark it 'failed' with error "Audit timed out" — this prevents a
     stuck audit from blocking a site forever if the container
     restarts mid-crawl

4. Frontend:
   - "Run Audit" button on the site detail page — calls POST
     /audit, then polls GET /audit/latest every 3 seconds until
     status is 'done' or 'failed'
   - Show a simple progress indicator while status is
     'queued'/'running'
   - Results dashboard: group issues by category (meta tags, headings,
     images, broken links, robots/sitemap), show counts and expandable
     lists of affected URLs
   - Handle the 'failed' state gracefully with the error message shown
     to the user

5. Important: write this defensively. If fetching robots.txt fails
   (404, timeout), don't crash the whole audit — treat it as "not
   found" and continue. If a single page fetch fails during crawling,
   log it and skip that page rather than failing the entire audit. The
   overall audit should only be marked 'failed' for genuine
   unrecoverable errors (e.g. the domain doesn't resolve at all).
